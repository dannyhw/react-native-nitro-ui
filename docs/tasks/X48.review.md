## Point 2: the entry swap

It is true on both platforms. `createHarnessEntryPointResolver` ignores the platform (`void platform`). It answers the
request for `<projectRoot>/index` with `@react-native-harness/runtime/entry-point`, and that file imports only
`react-native` and its own `./` modules. The resolver is placed first in the composite resolver, ahead of the user's
`resolveRequest`. Prewarm asks for the same entry through the same server. `example/index.js`, and with it
`App.tsx`, never enters a harness bundle.

The guard test (`gate-digests.test.js`, last `it`) reads strings from `node_modules`. It fails if the
config's `entryPoint` changes or the package renames the resolver or the entry. It does not fail if the
resolver stops being installed. That gap cannot produce a false green: without the swap the app registers
`App`, the harness UI never mounts, and the run fails on the bridge timeout.

## Point 3: `--rerun-failed`

| Case | Handled by |
| --- | --- |
| Digest moved between the red run and the completion | `planRerunFailed` reads the row as stale and refuses (`gate-core.mjs` `planRerunFailed`, `row.state !== 'red'`). `runGateUnclaimed` refuses again before the run (`gate.mjs:1412-1423`). `completeRerun` fails it a third time (`planned == null \|\| digestBefore !== planned`). |
| Tree changed during the completion | `completeRerun` fails on `digestAfter !== digestBefore`. A change outside the gate's digest still makes the line stale (`gateStateFor`, `treeAfter !== tree`). |
| Red run was filtered | A filtered run is recorded under its own name, so `listByGate(entries)[gate]` never sees it. The CLI refuses a filter or a colon name (`rerunFailedGate`, `command.split(':').length !== 2`). |
| Red run was a completion | Handled: `attempt` is incremented and `of` points at the original full run. Units are the merged set. |
| Units never run or with no result | Real-input: `selected` minus reported is `not-run`, and gets re-run. Harness: `files` minus reported is `not-run`. With no `files` the run is `unnamed` and refused. With no units file it is refused. |
| Every-run check failed while every control passed | Refused (`gate-core.mjs:2128`). The iOS a11y and tab methods ride every filtered run (`ios.mjs:434-435`). The Android sweep covers the whole table. Tree checks are scoped by `only` and folded into their control's unit (`android-tree-checks.mjs` `begin(\`${entry.id} (tree)\`)`). This is consistent. |
| Red run on another branch or worktree | The ledger is `.gates/<branch>.jsonl` under the worktree root (`gate.mjs:209-211`), read for `currentBranch()` only. |
| Two red runs | `gateRowFor` keeps the newest decisive line. |
| A completion fails and is completed again | Handled (test at `gate-rerun.test.js:292`). If the failed completion's tree moved, the line is stale and the older red run decides again with attempt 1. That is cosmetic. |
| Completion fails while the child exited 0 | **M3**: the background record and the ledger say exit 0. |
| `--background` | The child re-runs `gate.mjs <gate> --rerun-failed` (`gate.mjs:929-932`) and plans again. A filtered run is never recorded under the full name. |

## Point 7: two gates side by side in one worktree

Two leases held by one task are not what the lease tool hands out. `acquire` is idempotent per task:
`scripts/lease.mjs:282-294` returns the task's existing lease (`already: true`) whatever `--platform` asks for.

- The documented `acquire --task <id> --platform ios`, then `--platform android` in a second shell, gives the second shell the iOS
  lease. The Android gate is then refused by `deviceGateLeaseRefusal` (`leaseCoversPlatform`, "drives android, and lease … was
  taken for ios devices").
- With a `both` lease, both shells share one Metro port, and `metroPreflight` refuses the second gate. That is what the report saw.
- Distinct task names (`<ID>-ios`, `<ID>-android`) would pass every check: `NITRO_UI_LEASE_TASK` only has to match its own lease. That
  takes both device slots (`maxDeviceLeases: 2` in `scripts/devices.example.json`), so no other device task can run meanwhile.

What else two concurrent gates in one worktree share:

| Shared state | Effect |
| --- | --- |
| Ledger | One `appendFileSync` per run, which is safe. |
| Background records | Per log, so separate. |
| `.real-input/<p>/` | Per platform. |
| Build directories | `example/ios/build` versus the Android build directories, so separate. |
| `app.stamp` | Per platform. |
| `example/harness-run/state.json` | One file, shared by two harness runs. The docs already serialise the harness gates. |
| Metro transform cache | The default `$TMPDIR` cache, shared machine-wide already. The harness Metro uses `example/.harness`. |
| Tree check | Run outputs are git-ignored (checked with `git check-ignore`), so one run does not move the other's tree. A `build-app.mjs` or pod install run during the other gate can move the tree (N11). |

I expect the documented procedure to break at the second acquire, not at Metro.

## Nice to have

**N1. The literal check misses bare basenames.**
`gate-digests.test.js:350` ignores any literal without `/`, so `path.join(exampleDir, 'rn-harness.config.mjs')` or
`path.join(root, 'scripts', 'harness.mjs')` in a reached Node file would not be caught. My scan found none today. Also match the
basenames of the excluded files.

**N2. Harness tests can read files through the dev server.**
`example/__tests__/Button.harness.tsx:1712` fetches `src/assets/…` from Metro, and the walk skips the literals of in-app files
(`inApp`). A fetch of a non-asset `example/src/` path would go unnoticed. Scan the harness tests' literals for `src/` URLs outside
`assets/`.

**N3. A run-level failure is dropped when some unit also failed.**
`planRerunFailed` refuses only when no unit failed. A red run with one failed control and, separately, a run-level failure (for
example Android `e2e exited N` from a cleanup error) is completed by re-running that control alone. The child re-evaluates the
run-level checks for its own run, so the risk is low, but say so in `gates.md`.

**N4. Order dependence.**
A unit that fails in sequence and passes alone (state leaking between files or controls, for example recycling or a keyboard left
up) reads green after a completion. The brief accepted this. The `flake` skill should name it as a signal to check before
completing a merge gate.

`gate.mjs:1412-1423` has no test that reaches it, because the plan's refusal fires first. Cover it with a test, or drop it as
redundant with `completeRerun`.
