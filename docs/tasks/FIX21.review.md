## Findings

N1. `HybridNitroUiSearchField.kt:201,291,333`. Nothing in the composition reads `LocalConfiguration`, and there are no `LocalConfiguration` reads anywhere in `android/src`. The language change in the default RN/Expo setup recreates the activity: the example manifest has no `locale` in `configChanges`, and a per-app language on API 33+ restarts it too. In that case the new words do appear. An app that declares `locale|layoutDirection` and handles the change in place gets resources updated in place, but nothing invalidates the placeholder lambda or the clear button's semantics block. The old words then stay until something else recomposes. The claim "the next draw after a language change has the new ones" (`docs/components/search-field.md:171`, `.changeset/…:13`, KDoc `:70`) is therefore true only when the activity restarts. The cheap fix is to read `LocalConfiguration.current.locales` next to `LocalContext.current` and pass it as a `remember` key for the pair, the way `stringResource` does. The other option is to word the docs as "after the activity restarts".

N2. `HybridNitroUiSearchField.kt:75,91`. `object SearchFieldStrings` and `forLocale` are now public in a published package. Its `createConfigurationContext` path exists only for the probe. An app could call it, though it is unlikely to, and nothing is JS-visible. This follows no pattern the repo already has. The narrower in-repo options are a `nuiTest*` method on the SearchField spec (heavier: it touches spec and nitrogen) or `@RestrictTo` (lint-only, and not used in the repo). Acceptable at 0.x as a test seam. Worth a line in FOLLOWUPS if more probe-only Kotlin appears.

N3. `example/__tests__/SearchField.harness.tsx:736-738`. The German half asks the resolver for a context the probe built itself. The host half (`drawn.placeholder == appHint`, `hostClear == appClear`) runs on an emulator where the app's, application's and device's locales all match. So swapping the call sites to `context.applicationContext` (or `getSystem()` at the call site rather than in `entryFor`) would stay green. That matters below API 33, where AppCompat's per-app locale reaches the activity but not the application context, and `minSdk` is 24. The brief allowed a resolve-for-a-locale seam, so this is coverage, not a test that cannot fail. Mounting under a locale-overridden context is the only way to close it.

N4. `SearchField.harness.tsx:721`. `requestedLocale ("de") != appLocale` does not detect a German emulator, because "de-DE" is not "de". The `not.toBe(device*)` lines then fail, which is a false red, not a false green. The guard and its comment overstate what they check.

N5. `docs/tasks/FIX21.report.md:38`. "The clear button's label is read as the string the field applies" is not what happens. `hostClear` is the probe's own `forLocale(host.context, "")` (`NitroUiProbePackage.kt:94`), not the label the field set on the button.

N6. `docs/components/search-field.md:85`. The edited table row is 251 characters, while the other rows are 249, so its closing pipe is out of line. `check` accepts it.
