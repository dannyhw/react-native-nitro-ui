## Summary

**Per-gate digests.** Each device gate has its own digest: its platform half less the paths only
the other suite reads (`GATE_DIGEST_EXCLUSIONS` in `scripts/gate-core.mjs`). `status`, `need`
and `table` read it; review asks for a harness gate only when the diff touches that gate's
files. Ledger v7 adds `gateTrees`, `units` and `completion`. A line without `gateTrees` is
compared on its platform half, which is unchanged. Moves, checked on the real tree:

- `example/e2e/real-input/form.e2e.ts` → `real-input:android`
- `example/__tests__/Form.harness.tsx` → `harness:ios`, `harness:android`
- `example/src/FormScreen.tsx` → `real-input:ios`, `real-input:android`
- `src/` → all four
- `scripts/real-input/android-tree-checks.mjs` → `real-input:android`

**Proof.** `scripts/__tests__/gate-digests.test.js` walks each run's imports with the repo's
TypeScript parser. It fails when a run reaches, or a reached Node file names, a path its digest
leaves out. It also checks that react-native-harness swaps `example/index.js` for its own
entry. Harness tests require `example/src/assets/icons/*`, so assets stay in. Also kept:
`scripts/harness-run-state.js` (Metro requires it), `uiautomator.mjs` (iOS a11y imports it),
and the UI-test target in `harness:ios` (unproved).

**`--rerun-failed`.** It completes the newest red full run on this digest. It re-runs failed
and never-run controls or harness files and records the result under the full gate. Real-input
writes per-control results; the harness plugin now records its file list. It refuses on no red
run, a moved digest, no per-unit results, a failed isolated suite, or an every-run-only failure.
The table shows `completed: N of M units re-run, attempt K`.

**Device.** With the keyboard preference YES, full `real-input:ios` was red on Form only (1 of
28) in 49 m 24 s. Set back to NO, `--rerun-failed` re-ran `--control form` and passed in
13 m 49 s, mostly the UI-test rebuild. An earlier pod-less build failure was refused as "no
per-unit results".

**Side by side: not proven.** Under the same lease, `harness:android` started 7 s after
`real-input:ios` was refused ("Metro port 8293 … is served by pid 20715"). One lease has one
Metro port, and a harness Metro serves the harness entry, so one lease cannot work. Two leases
were unavailable: X47 held the other pair and X46 was queued. The only other shared state found
is the harness run-state file under `example/harness-run/`, which matters only for two harness
runs.
