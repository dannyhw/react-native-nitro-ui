1. **Blocking.** `scrollToTop` (`scripts/real-input/a11y-sweep-device.mjs:359`) still gives up
   after 8 half-window swipes. `treeShowing` now scrolls as deep as a page goes: about 7,200 px on
   Host and 11,700 px on DatePicker, measured in this task. The next case's `scrollToTop` can then
   stop short of the top. This is most likely on a runner, where each swipe moves the page less.

   runs next and sits near the top. `scrollToTop` stops mid-page after 8 swipes, `treeShowing`
   scrolls down from there, never meets the control, and reaches the page end. The case fails
   with "not in the tree". The fix is for `scrollToTop` to stop on the same page-end rule as
   `treeShowing`, under the same kind of stated cap, and not on a fixed 8.

   `scrollToTop`. On a runner, dropped input is exactly the slow-machine case this task is for.
   Failure scenario: one dropped swipe while the control is still below the window. The probe
   ends early and grades a control that is off screen, which is the original failure. Count the
   page as ended only after two swipes in a row leave it where it was.
3. **Non-blocking.** A truly missing control on a 200-row screen costs about 100 swipes before
