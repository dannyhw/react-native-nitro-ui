# X60 review — round 1

**Verdict: fix round needed** (1 blocking, 5 non-blocking)

Reviewed `origin/main...HEAD` at `d290bfb4`. The loop shape is right: Back goes only to an
`app-window`, or to the app's activity while its keyboard is up. `startFromLaunch` sends none.
Each `continue` uses up one of the `backs`, so the loop always reaches its deadline check.
`am start` is rate-limited to once every 3 s. Behaviours 1–4 hold as long as `readWindowFocus`
reports the live focus. Finding 1 shows a common device state where it does not.

## Findings

### 1. Blocking — a saved ANR makes `readWindowFocus` read a stale focus for up to two hours

`scripts/real-input/window-focus.mjs:27-30` takes the **first** `mCurrentFocus=` in the full
`dumpsys window` print, and `windowBlock` (`:60-64`) takes the first matching `Window #` header.
With no arguments, `dumpsys window` prints `WINDOW MANAGER LAST ANR (dumpsys window lastanr)`
first. After any ANR since boot, that section holds a full copy of the window list and of the
display contents (`Last ANR continued` → `mCurrentFocus=…`) as they were at the ANR. The window
manager keeps that copy for two hours (`LAST_ANR_LIFETIME_DURATION_MSECS`). The test fixture
(`real-input-window-focus.test.js:60-75`) has no such section. It also puts the windows before
the display contents, which is the reverse of the real order, so it cannot catch this.

Checked against the code as written (scratch probe, not committed):

```
ANR(null) + live dump     -> { title: null, owner: 'none' }      live focus is the app's activity
ANR(launcher) + live dump -> { title: '<launcher>', owner: 'other' }
```

Failure scenarios:
- On a slow runner the usual ANR is "Application does not have a focused window", raised when
  an input event arrives during a launch. It is saved with `mCurrentFocus=null`. From then on,
  every `awaitApp` reads `none`. `startFromLaunch` waits its whole 120 s and throws
  `… The focused window was none (none)`, although the app is up and focused. That repeats on
  every run for two hours. This is exactly the environment the task targets.
- A "System UI isn't responding" or launcher ANR saves focus on a launcher or system window.
  Every read is then `other`: `am start` or `cmd statusbar collapse` every 3 s, then a throw
  that names a window that no longer has focus. Behaviour 3's message becomes misleading.
- Leased emulators stay booted between tasks, so an ANR from an earlier task's run poisons
  local runs the same way.
- If the saved focus was the app's own activity from an earlier process, every read is
  `activity`. `startFromLaunch` then goes back to returning on the first dump that shows a tab
  bar, which is the closing-task race this task fixes.

Fix direction: read only live state. Either run `dumpsys window displays` (focus) and
`dumpsys window windows` (window list) as two commands, since neither prints the last-ANR copy,
or ignore everything up to the last `WINDOW MANAGER DISPLAY CONTENTS` header. Note that the ANR
copy prints that header too, so it must be the last one. Add a fixture with a leading
`LAST ANR` section whose focus is `null`, and one where it names the launcher. Red proof: the
current parser returns `none` or `other` on them.

### 2. Non-blocking — with more than one display, the first display's focus wins

`window-focus.mjs:27-30`. `dumpsys window displays` prints one `mCurrentFocus=` per display.
Their order follows the display hierarchy, not "the display the app is on". Suppose a virtual
or secondary display is printed first with `mCurrentFocus=null`, for example an emulator
started with `-multidisplay` or an app that created a presentation display. Then every read is
`none` and the launch times out (probe: `2 displays -> { owner: 'none' }`). The gate's
emulators have one display, so this is latent. If it is cheap, prefer the block for
`mTopFocusedDisplayId` or `mDisplayId=0`. If not, put one line under Follow-ups.

### 3. Non-blocking — a relaunch between checks is silent

`a11y-sweep-device.mjs:165-175`, reached from `returnToAppWindow`
(`android-tree-checks.mjs:874`). Suppose a check passes and the app then dies (a crash on
dismissal, say). Focus becomes the launcher. `awaitApp` runs `am start -n …/.MainActivity`,
which cold-starts a fresh process, and the next check passes on it. The old code pressed Back
three times, and the next `goToScreen` failed visibly. No state a check depends on is reset in
the middle of a check: `returnToAppWindow` runs only between checks, each check starts with
`goToScreen`, and while the task is alive `am start` with the same root intent only brings it
to the front. But a crash between checks is now hidden. Suggest that `awaitApp` take the
check's `log` and `note` each bring-forward, or that `returnToAppWindow` refuse to relaunch a
process that is gone (the app's `pid` is missing from `pidof`).

### 4. Non-blocking — the focus check and the Back key are separate commands

`a11y-sweep-device.mjs:160-163`. The `app-window` branch reads focus, then starts a new
`input keyevent 4` process, which takes about 0.5–1 s on a slow runner. A popup that starts its
exit animation in that gap loses focus to the activity. The Back then reaches the activity, and
with no JS back handler that finishes the app. This is narrower than the old code, which sent
Back blind, and the central behaviour holds after a relaunch (`backs: 0`). Between checks it is
still a path to closing the app. A cheap hardening: require the same `app-window` on two reads
in a row before sending Back. Not needed for this round.

### 5. Non-blocking — no test for the package-prefix case

The brief asks about `nitroui.example` against `nitroui.example.dev`. The code handles it:
`block.package !== appId` is an exact comparison (`window-focus.mjs:41`), and the fallback
checks `startsWith(`${appId}/`)` with the slash (`:38`). The probe returns `other` for a
focused `.dev` activity. No unit test covers it, though, so a later switch to `startsWith` or
`includes` (as `popup-windows.mjs` uses) would pass the suite. Add one assertion. I found no
input other than findings 1–2 that makes a foreign window read as the app's, or the app read as
foreign.

### 6. Non-blocking — the test fixture is built from the parser's own assumptions

`real-input-window-focus.test.js:12-20, 60-75`. `windowEntry` and `dumpsysWindow` emit exactly
the shape the regexes expect: windows before display contents, one display, no ANR copy. The
report says the format was checked against a real dump, but none is in the tests. A trimmed
real dump, with hashes and titles anonymised, should be the fixture for `readWindowFocus`. That
fixes the order and would have shown the section in finding 1 on any device that had seen an
ANR. The behaviour tests' scripted device is sound otherwise. The read state advances only on
`dumpsys window`, and hierarchy, IME and focus answers come from the same step, so the fakes do
not coincide with the right answer.

## Other checks

- **Red proofs**: all three are plausible for the code as written. With old `returnToAppWindow`,
  the scripted device never advances (it makes no `dumpsys window` read), so it sends 3 Backs on
  launcher, splash and popup states (`expected 3 to be +0`, `expected 3 to be 2`) and resolves
  instead of rejecting. The old `startFromLaunch` loop returns on the first `TABS_XML` with no
  focus read (`expected [] to have a length of 3`). That only holds if `-W` was kept during the
  mutation, otherwise `toContain('am start -W …')` fails first. The report says only the loop
  was reverted.
- **Timeouts/retries (AGENTS.md)**: the launch keeps 120 s. The 30 s return bound replaces an
  unbounded-but-short three-Back loop and is part of the fix the brief asks for ("waits for the
  app"). No retries were added, and no assertion was loosened.
- **Comments**: no task IDs, decision numbers or history in the new code or tests.
- **a11y sweep, fast-machine path** (Behaviour 4): `startFromLaunch` now (a) launches with
  `am start -W`, which blocks until the launch is reported and is bounded by the system's launch
  timeout, (b) adds a full `dumpsys window` per poll, which is large but well under `run`'s
  64 MB `maxBuffer`, and (c) requires `android:id/content` as well as `example-tabs`, as
  `returnToAppWindow` already did. With `backs: 0`, a focused window of the app's own at launch
  is waited out to 120 s instead of being ignored. Nothing of that kind appears on the example
  app's launch: the RN dev loading banner is a non-focusable popup. On a device with no saved
  ANR, the local path behaves the same apart from one extra command per poll. Finding 1 is the
  one way it changes locally.
- `node scripts/gate.mjs check` in the worktree at `d290bfb4`: PASS (18 passed, 0 failed, 58 s).
