## Summary

Four rules, one parameterised suite, driven by `src/components/*/component.json`. The rules
are data in `scripts/conformance-core.mjs`; `coverageMatrix` + `formatMatrix` print the
rule × control table below, and `checkCoverage` refuses a cell that is neither covered nor
marked `failing` with a `FOLLOWUPS.md` line that actually exists. A new manifest is covered
the day it lands — `checkInAppFixtures`, `checkA11yTable` and `checkCoverage` each go red in
`check` if it is not — so 0.4's Menu inherits all four rules with nobody writing a case.

**Where the Android a11y rule runs, and why.** The in-app harness matches
`View.contentDescription`; Compose publishes a control's name on a `SemanticsNode` that is not
a `View`, so a hosted control's name is invisible to any in-process query — the gap
`Slider.harness.tsx` and `Progress.harness.tsx` each already record. `uiautomator dump` *is*
the accessibility tree, so the rule reads that, from the host, **inside
`scripts/real-input/android.mjs`** after its `CHECKS` loop: not a new gate, but a ride on a run
that already boots the app, walks every tab and pays for dumps. `Suite.beginAuxiliary` keeps the
sweep out of the control totals while still failing the run. iOS asserts the rule in-app, where
`queryByAccessibilityLabel` does reach through the SwiftUI host.

**Nothing asserts against its own copy.** Fallbacks, poison sizes, tolerance, box rules and
in-app debt rows live in one marked JSON region in the harness file, regenerated by
`scripts/conformance/print-shared-table.mjs` and compared with `sharedInAppTable()` on every
`check`. The poison (`97×11` / `111×13`) belongs to no control, so "the box was right" can only
mean a correction arrived.

**Debt, not fixes.** Four a11y findings (Slider, SegmentedControl, each hosted too) are exempted
per *finding*, and `staleDebt` goes red when a row stops matching something real: the list
clears itself with a failing test rather than a reviewer noticing.

**What the runs cost.** Three of this branch's commits fix what the suite's first device
runs broke:
the fallback rule assumed `measured ≈ declared`, false by design for a `fillWidth` control's
width and for Button (see the box-rule section under Red proofs); the harness's 1 s mount
default, which every other suite works around; and two ways `task-ready` disagreed with its own
documentation. An existing guard also went red while being right: a Metro orphaned by a run I
killed held the lease's port, the harness moved to 8294, and the timing gate refused to trust
its own numbers.

## The rule the device run corrected

The first fallback run went red on three of seven controls, and the rule was the wrong part. It
asked every control for `measured ≈ declared`:

- a `fillWidth` control's width is its **parent's**. Slider measured 420 wide on a 420 dp screen
  and declares 328, and both statements are true — the declaration is what the first frame is
  laid out at, before the parent is known. Its height is its own, so that half is still compared
  and a stale `FALLBACK_HEIGHT_DP` still goes red.
- `NitroUiButton` is `intrinsic` but *content-sized*: `docs/components/button.md` measures 33.3
  to 103.2 wide across titles and variants, and its declared pair is documented as the middle of
  that table. The fixture measured 57.3×34.3 on iOS, 77×48 on Android. Comparing a box with a
  documented guess asserts nothing about the component.

`boxRuleFor` now derives the axis from the generated sizing policy (`both` / `height` / `none`),
and `boxRules` travels in the mirrored table so the suite that asserts cannot choose its own
rule. The warm "needed no correction" assertion applies only where the declaration does describe
the whole box. Button's exemption has to earn itself every run: `checkContentSizedBox` refuses a
name that is not an `intrinsic` control, and `fallbackFindings` refuses a member whose box turns
out to equal its declaration anyway — so adding a name to get one run green buys one run.

## What the Android sweep found on device

13 cases, one pass at the end of `real-input:android`, after the control checks. Nine clean,
four `known failing` — precisely the four the fixtures predicted, and the run prints each one's
FOLLOWUPS line so the debt is in the transcript, not only in a source file:

```
a11y:slider: the node that carries "Controlled slider" is not actionable, and nothing whose box
  is the control's is either (android.widget.SeekBar no actions [42,738][1038,864]) … The nearest
  actionable box containing it is a android.widget.ScrollView [0,384][1080,2424] focusable,
  which is the page, not the control
a11y:segmented-control / a11y:hosted-slider / a11y:hosted-segmented: same shape
```

Two things that measurement alone settled. The name *is* published — `content-desc` carries the
label on a real `SeekBar`/`View`, so this is not the missing-label bug, it is the label-and-action
split the G5/G6 reviews found by hand. And the containing actionable node is the page's
`ScrollView` every time, which is why the rule rejects "something actionable contains it" and asks
for a box that *is* the control's. `staleExemptions` matched all four rows, so the debt list is
describing real findings and nothing else; the run still exits green because these four are the
recorded debt, and it would exit red if a fifth appeared or one of these four stopped matching.

## Follow-ups

- Android a11y: the four exempted nodes may be a dump artefact — `uiautomator dump` runs without touch exploration, so Compose may mark a node focusable only once TalkBack is up. `FOLLOWUPS.md` names the measurement that settles it.
- Android a11y: Progress's own screen can never be dumped (indeterminate indicators never idle), so what a screen reader announces for an *animating* indicator is unasserted; `hosted-progress` covers the determinate one.
- The recycle rule measures identity, not recycling — `enableViewRecycling` appears nowhere in `src/` or `example/`, so the fixture hands one `testID` to a second owner rather than reaching `prepareForRecycle`.
- Two ways the same run went wrong, both fixable in front of the run rather than after it:
  `harness.mjs` falls back to the next Metro port and keeps going (only the wall-clock timing
  guard noticed, by comparing the published port with its own — the state file is
  `scripts/harness-timing-gate.js`'s, and the run reads it back over Metro), and
  `lease.mjs` hands out the first pair *no lease* holds without asking whether a gate process is
  live on it — F7's harness outlived its own lease, so pair-a read as free and the pool gave it
  to me twice. A `gate.mjs` pre-flight that refuses a leased Metro port already serving someone
  else turns a lost 3-minute run into a 1-second message; I wrote that check into my own wrapper
  and it fired immediately on the first retry. The sharpest symptom, worth recording: with two
  tasks pointed at one Metro port, the harness fails as
  `The app bridge was replaced by a newer app connection` — F7's iOS app joined my Android
  run's Metro (`platform (prewarm=android, app=ios)`) and its files died mid-suite with zero
  failed assertions.
- Two pre-existing ESLint warnings are on `main` and in files this branch does not touch:
  `scripts/harness-suite-timing.mjs:25` (`join` unused) and
  `scripts/__tests__/registry.test.js:651` (`manifests` shadowed).
- `scripts/conformance-core.mjs` and friends count as both platforms in `gate.mjs` (they are not in `TOOLING_FILES`), so a rules-only edit owes two harness runs. Deliberate for `real-input/*`; arguable for `conformance-core.mjs` alone, and left as the expensive-but-honest default.
- task-ready's citation check has a blind spot it cannot close from git alone: a path that
  exists only at runtime (the timing gate's state file, `.real-input/<platform>/…`, anything
  gitignored) is a fair thing to cite and reads as an invented file. The rule needs a small
  allow-list of generated-at-run-time roots, or a report has to avoid naming them in backticks
  — which is what this report now does. Found by the report's own first full run, twice: the
  first time in the prose, then in this very line about it.
- `real-input:ios` is not required for this round (nothing iOS real-input was added), and it
  was run anyway as a regression check on `support.mjs`: `Suite.finish` is shared and the
  `auxiliary` list now prints in its summary on both platforms. Green, 11 m 26 s.
- `checkA11yTable` proves a case's `screen`, `anchorTestId` and `label` exist in the screen
  file, so it caught Menu's missing case at the merge — but not what happens when a screen
  grows a *second* node with the same `testID`. G7b's real-input block and my round-2 a11y
  block both added `real-input-menu` to `MenuScreen.tsx`, which would have made the rule's
  box comparison compare against whichever of the two a traversal happened to reach. I fixed
  the collision by hand; the guard would not have. A duplicate-testID check over
  `example/src/*.tsx` is a few lines and belongs with the other cross-checks.
- Two device runs failed for reasons of mine, and the ledger keeps them: I started a Metro on
  the lease's port by hand (the harness publishes its machine state over Metro, and the
  timing gate refused the run when the state file named a different port than the one it was
