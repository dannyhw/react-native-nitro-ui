# X3 — Component registry and codegen

**Worktree / branch:** named in your delegation message (from `main`).
**Round cap:** 1 implementation round plus at most 2 fix rounds (D19).
**Devices:** from `node scripts/lease.mjs acquire --task X3` (CONTRIBUTING "Leasing a device or
port"). Release the lease when you finish. **Finish by 00:30 local:** an exclusive bench job starts at
01:00, and `--exclusive` waits until every other lease has ended.

## Why

`docs/tasks/PROCESS-review-2026-10-26.md` §2 ("Merge-main conflicts") and §4 row 5: each new control
is added by hand to about 15 lists across the repo. The four component merges conflicted in 17–29
files each. That stops two components from being built in parallel.

## Do

1. **One manifest per control:** `src/components/<Name>/component.json`, covering the seven controls
   (not `Host`). It holds the facts the lists below repeat: the name, the Hybrid View name and
   implementation class, the kebab id, the sizing policy (`intrinsic` / `fillWidth`), whether it is
   hostable, the example tab, and whether it is in the bench, smoke and real-input sets. Keep the
   schema to what the generated lists actually read, document it in one place, and validate it
   (unknown keys and duplicate ids are errors).
2. **`scripts/gen-registry.mjs`** (`bun run registry`) writes these lists from the manifests:
   - `nitro.json` `autolinking` and `nitro-ui.sizing.json`;
   - `NitroUiPackage.kt`'s manager list, and both `NitroUiDeclaredFallbacks` (`.kt` and `.swift`);
   - `src/components/Host/HostChildren.ts`'s `HOSTABLE_CONTROLS`, and the `src/index.ts` exports if
     the export names can be derived without special cases (otherwise leave `index.ts` hand-written
     and say so);
   - `src/__tests__/viewConfigs.test.ts`'s `copies`;
   - `bench/src/types.ts` `ComponentName`, `bench/src/plan.ts` `SUFFIXED_COMPONENTS`, the
     `nitro-ui-host` component arrays in `bench/src/implementations/index.ts` and
     `scripts/bench/lib.mjs`;
   - `scripts/smoke/lib.mjs` `SMOKE_CONTROLS` and its duplicate in `scripts/smoke/App.tsx`;
   - `scripts/real-input/controls.mjs` `REAL_INPUT_CONTROLS`;
   - the example `App.tsx` `Screen` union, `TABS` and screen switch.

   Per-control behaviour code (the `component === '…'` branches in bench arms, harness tests,
   Android `CHECKS`, `RealInputTests.swift`, docs prose) stays hand-written. Where a hand-written
   table must cover every control, add a test that fails when one is missing (like
   `src/__tests__/host.test.tsx`), rather than generating it.
3. **Generated output style.** In shipped files (`etc/package-files.txt`) the generator must
   reproduce **today's bytes exactly** from the current manifests. The published package must stay
   byte-identical (ORCHESTRATOR "Rules"), so no new marker comments or headers go in shipped files. In
   unshipped files, `// @generated by scripts/gen-registry.mjs` begin/end markers around the region
   are fine. Prefer moving a list into its own small generated file where that leaves the shipped
   package unchanged.
4. **Drift check in `bun run check`** (`registry:check`, like `nitrogen:check`): it regenerates into
   memory and fails on any difference, naming the file. Show it red: edit a generated list by hand,
   and also edit a manifest without regenerating.
5. **Merge rule.** Make conflicts in generated output cheap: `.gitattributes` marks the registry
   outputs and `nitrogen/generated/**` as `linguist-generated`. Add a `bun run regen` that runs
   nitrogen plus the registry. Document the merge recipe in CONTRIBUTING: on conflict in generated
   files, take either side, then run `regen`. Don't rely on a custom merge driver that needs
   per-clone git config unless `doctor --setup` installs it.
6. **Proof that it worked:** in a scratch clone outside the repo, make two branches from your tip.
   Each adds a fake control: a manifest, a `.nitro.ts` and a stub `.tsx`. Native stubs only if
   nitrogen needs them, and none are committed. Merge the two branches and record the conflicted
   files. Do the same experiment on `main`'s layout (hand-adding to the lists) for the before
   number. Report both counts. Delete the scratch clone.
7. **Docs:** CONTRIBUTING "Adding a component" (or the closest section) becomes "add a manifest,
   run `bun run regen`", plus the hand-written files that remain.

## Out of scope

The conformance suite and `task-ready` (X4). Changing any component's behaviour. README / component
prose. Bench plan contents (the generator writes today's rows).

## Gates

- `node scripts/gate.mjs check` green, then `node scripts/gate.mjs need --for review` satisfied:
  the diff touches `android/`, `ios/` and `example/`, so both harnesses are needed. Build both apps
  first (`node scripts/build-app.mjs --platform <p>`).
- Package byte-identical: `npm pack` file list = `etc/package-files.txt`, and the packed file
  contents are unchanged against `main` (compare tarball file hashes, and give the command you used).
- Report: `docs/tasks/X3-component-registry.report.md` (REPORT-TEMPLATE), with the before and after
  conflict counts from step 6, and the ledger exported with `node scripts/gate.mjs export --task X3`.
  Commit on your branch, don't push.
