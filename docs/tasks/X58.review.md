## The Linux question

**The report's premise is wrong, and no other cut-off path exists.** Node does not write to a
stdout pipe synchronously on Linux. Node 24.21's own `net.js` (read from the running binary)
makes a stdio pipe blocking only when `isWindows`: in the `net.Socket` constructor,
`(fd === 1 || fd === 2) && this._handle instanceof Pipe && isWindows` → `setBlocking(true)`.
`createWritableStdioStream` (`internal/bootstrap/switches/is_main_thread`) builds a plain
`net.Socket` for `PIPE` on every platform. On Linux, libuv opens the pipe non-blocking. A
write larger than the free pipe space (64 KiB by default) is written in part, and the rest is
queued. `process-exit.js` `exitAfterFlush` then waits at most 2 s (`Promise.race` with the
sdk-io sleep) before `process.exit`. So the Linux CI cut-offs are the same race as on macOS.
This fix covers them.

I traced every other step from the daemon to stdout in `node_modules/agent-device/dist/src`.
None of them can hand the parent a short answer with a zero exit:

- **The daemon reply is parsed whole before anything is printed.**
  - Socket path: `daemon-client-transport.js` `yt` collects lines through `transport.js` `n`.
    Each line goes to `_t().handleLine`, which runs `JSON.parse` on it. A reply cut short at
    `end` goes to `B`, which raises `Invalid daemon response`.
  - HTTP path: `Mn` reads the body with `transport.js` `i`, which resolves only on `end`. It
    then runs `Dt` → `Ot` (`JSON.parse`). A body cut short raises `Invalid daemon response`,
    an abort raises `Failed to read daemon response`, and a stall hits the request timeout.
  - All three end as `COMMAND_FAILED` with exit 1, never as partial stdout.
- **The answer is one write.** On success `generic.js` `u` → `shared.js` `e` → `json.js`
  `printJson` makes a single `process.stdout.write(JSON.stringify(…, null, 2) + "\n")`. Then
  `process-entry.js` `runCliProcess` → `exitAfterFlush(0)`.
- **`exitAfterFlush` is the only exit after a successful write.** The other `process.exit` in
  the CLI path is `internal/bin.js`'s `.catch(() => process.exit(1))`, and it runs only on a
  throw, with a non-zero code.

So once stdout is a file, nothing is left to cut the answer short.

## Findings

1. **Non-blocking — the report's Linux follow-up is a false claim.**
   - Where: `docs/tasks/X58.report.md:68`.
   - What: the follow-up says Node writes to a pipe synchronously on Linux, so the pipe mutation
     "probably stays green there". Per the section above, Linux pipes are non-blocking.
   - Failing case: on Linux the stand-in writes about 6 MB, and only the first part fits in the
     pipe. `process.exit(0)` follows at once, so the pipe mutation should go red on Linux as it
     does on macOS. `check` runs this test on `ubuntu-latest` in `ci.yml`.
   - Fix: replace the line, or drop it. The fix and its test are not affected.
2. **Non-blocking — when the driver fails, its own reason is deleted unread.**
   - Where: `os-tree.ts:117-127`.
   - What: with `--json`, the driver writes its error as JSON to stdout, not stderr.
     `cli.js` `J`, `ve` and `we` each call `W({ success: false, error })` and then `w(1)`.
     `execFileSync`'s message carries only `Command failed: <argv>` plus stderr. The error JSON
     now sits in `snapshot.json`, which the outer `finally` removes without reading.
   - Failing case: the driver answers `{"success":false,"error":{"code":"DEVICE_IN_USE",…}}`
     on stdout and exits 1. The thrown message is `…failed: Command failed: …/node
     …/agent-device snapshot --json … --session e2e-android-0`, with no code and no reason.
   - This loss already existed before the change (the old code dropped `error.stdout` too), so
     Behaviour 2 ("as it does now") is met. With the answer already in a file the read owns,
     adding it to the message is cheap.
   - Follow-up only. Changing it now would go beyond Behaviour 2.
3. **Non-blocking — the failure test uses an error shape the real driver does not produce.**
   - Where: `scripts/__tests__/os-tree-read.test.js:105`.
   - What: the stand-in writes `DEVICE_IN_USE` to stderr. The real driver in `--json` mode
     writes it to stdout (finding 2).
   - The test does guard what it claims: the failure path, the "failed" prefix, stderr in the
     message, and the directory removed. But it suggests a driver failure's code reaches the
     message, and finding 2 shows it does not.
   - Fix (with finding 2, or not at all): add a stand-in that writes the error JSON to stdout
     and exits 1.
4. **Non-blocking — a read killed by a signal leaves its directory behind.**
   - Where: `os-tree.ts:92` and `:127`.
   - What: `execFileSync` blocks the thread. If the suite's process gets `SIGINT`, `SIGTERM` or
     `SIGKILL` during the read (Ctrl-C, or a runner killing its worker), Node's default handler
     exits without running `finally`.
   - Failing case: Ctrl-C during a DatePicker read leaves `$TMPDIR/nitro-ui-tree-XXXXXX/` with
     a partial `snapshot.json`, up to a few MB.
   - The driver's own timeout is handled (see "Checked"), and it is in the OS temp directory,
     which the OS cleans. Behaviour 3 ("pass or fail") is met. A sweep of stale
     `nitro-ui-tree-*` directories would close the gap. I do not recommend one at this size.
5. **Non-blocking — no test guards the fd `closeSync`.**
   - Where: `os-tree.ts:123`.
   - Failing case: with `closeSync(fd)` deleted, all 4 tests still pass (re-run here). That
     leaks one fd per `tree()` call. A full Android run reads the tree many times, so the leak
     is slow and harmless at today's counts.
   - The code is right as written. This finding is only about test coverage, and no change is
     required.
