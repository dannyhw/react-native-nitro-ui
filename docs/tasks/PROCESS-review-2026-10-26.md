# nitro-ui: process review (where the time went, how to move faster)

Scope: 22 Oct 17:15 to 26 Oct 12:15 UTC (91 h elapsed, ~29 tasks). Sources: git history (489 commits), `docs/tasks/*`, the orchestrator transcript (`8844c121….jsonl`: 97 `delegate_task`, 52 `Agent`), and the T3 `statev2.sqlite` turn items (25,938 Apex shell commands with start and end times, read from a copy). Times are UTC. Git shows BST (+1 h) before 25 Oct 01:00.

| # | Change | What it removes | Est. saving per cycle like this one (~90 h) |
|---|---|---|---|
| 1 | **Take benches and baselines off the dev machine.** Run them on the second Mac, or failing that in one nightly batch. No quiet windows on the main machine. On a provider 429, retry with backoff before asking the owner. | 15.1 h with no Apex or Opus work running. Of that: 7.2 h overnight after R2 waiting on owner decisions, 5.3 h idle before the two quiet windows, and 1.6 h on a 429 outage while the orchestrator sat in `AskUserQuestion`. | **8–10 h** |
| 3 | **A per-component conformance suite and a `task-ready` script before review.** Generic checks driven by the registry: Android a11y label on the focusable node, MountChurn leak on drop, declared fallback registered and different from the measured size, every new test has a recorded red. | The recurring must-fix classes behind fix rounds. Fix rounds took 27.6 h against 34.8 h of implementation (44 % of Apex time). Three tasks used both fix rounds (G1, G5, G6). | **6–9 h** |
| 4 | **A gate ledger with targeted fix-round gates.** Results are keyed to the code tree hash, so docs-only commits don't invalidate them. The report's gate table is generated. | 5 | **A component registry with codegen for every registration point.** Pair it with a merge rule that regenerates nitrogen instead of hand-merging it. | Component merge-main passes conflicted in 17, 24, 23 and 29 files (G2, G3, G4, G6: 93 files), 24 of them generated by nitrogen. Also the G6 merge-main pass (65 min of Apex time plus full gates). This change is also what makes parallel components on two machines safe. | **3–5 h direct, and it unblocks #1/#5 parallelism** |

Next after these: (6) a fresh-build-and-verify helper plus a device lease file, which removes 6 stale-binary incidents and the per-brief device boilerplate (~4 h). (7) Turn GitHub CI back on for `bun run check` and the Android release build (~1 h, plus a clean-checkout signal).

**Second machine verdict: yes, as the bench/quiet environment first, and a second device pair later.** On its own as the bench host it saves ~15–25 % of calendar time for the same scope. With the registry (#5) and a lease file it allows 3–4 device tasks, up to ~1.5× component throughput. Baselines must be re-minted on that machine and gated only there.

## 3. Process overhead: what is worth it, what isn't

- **Opus review and re-review: keep.** It is cheap (avg 9.6 min) and finds real bugs. Examples: the H1 Host never calling `drop()` (B1's leak again), the G6 sizing-cache poisoning, and Android a11y on the wrong node twice. Re-review only after native changes (D19) is right.
- **Fix rounds are expensive because of what they re-run.** Each one re-runs the full harness on both platforms, real-input on both, often both benches, and then the gates again "on the final tree" after doc commits. Safe to cut:
  - Fix rounds run the touched platform and suites only, plus `bun run check`.
  - The full harness and real-input run once on the merge candidate.
  - Bench only when a perf-path file changed, and only on the bench host.
  - Doc-only commits never trigger re-runs, which the tree-hash ledger enforces.
- **"Every new test shown red": keep the rule, but make it cheap.** G6 has 60 "red" mentions and 11 mutation rows. Record mutations as data (`docs/tasks/<id>/mutations.json`: test, mutation diff, red log) produced by a helper. Then the review checks it mechanically and the report prose stays short.
- **Report format: shrink it.** A ≤ 400-word summary, a generated gate table, follow-ups as one-liners, and questions. Anything else goes in an optional appendix. Fix rounds append ≤ 200 words. Drop device-hygiene boilerplate; the lease and the scripts enforce it.
- **Bookkeeping.** 97 of 122 orchestrator commits on main touch STATUS/RECOVERY, and there were 106 Bash edits of those files. RECOVERY duplicates STATUS plus `git worktree list`. Turnaround is under 1 % of time, so this costs tokens more than wall-clock. Generate both files from one `docs/tasks/tasks.json` with a script, and commit once per merge rather than once per state change.
- **Task size.** G5 and G6 (popup or dialog components) are the outliers. Split each component into (a) the native component with harness and sizing and (b) the bench arm, real-input case, Storybook and smoke. Then review of (a) starts hours earlier and (b) can run on the bench host.
- **More parallelism on one machine: no.** Two device tasks already push load1 to 20–200 and cause most of the flakes. On two machines: yes, once #5 (registry) and the lease exist.

## 5. Second machine plan

**Would it help? Yes.** The constraint is one 14-core machine doing three things that conflict: two device tasks (load 20–200), benches that need load < 7, and the owner's own use. About 15 h over 4 days was reserved for quiet windows (A1b 20:29→06:15, A1c 23:13→04:51, including the idle run-up). Every daytime bench ran "busy".

**Phase 1: bench/quiet host (do first).**
- All `bun bench` runs move there: in-round quick plans, `--compare` and `--update-baseline`. So do the long cold-sizing and `HARNESS_TIMING=1` timing gates (D21), which need a quiet machine.
- Rounds on the main machine stop benching. They submit a job (automation #1) and continue to review. The bench result is attached before merge, or follows as a bounded follow-up per D15.
- **Baselines:** re-mint both canonical baselines on mac2, using the same device *classes* (an iPhone 17 simulator on iOS 27, which gives key `ios27-sim-iphone17`, and an API 35 Pixel 9 AVD, `android35-emu-pixel9`). That is ~3 h each, back to back, any time of day. After that, gate `--check` only on mac2. Add a check that refuses `--check` when `machine.cpuModel`/`hostname` differs from the baseline's recorded machine. The metadata is already recorded (`scripts/bench/render.mjs:400`); keys are class-level (D15).
- **Comparability:** baselines store launch-paired ratios to `rn-core` (`bench/baselines/README.md`), so host speed mostly cancels. But simulators and emulators run on the host CPU and GPU, so UI-CPU ratios can shift with core count, GPU and memory pressure. Memory KiB/instance is the most portable metric. Don't mix machines for gating. To quantify the drift once, run one `--plan quick` on the same SHA on both machines (~10 min each). If ratios agree within their spreads, main-machine quick runs stay usable for rough local checks only.

**Phase 2: second device pair (after the registry, #5, and the lease, #7).**
- One or two more device tasks (a component or Host task) run on mac2 with their own lease file. Do this only once registration points are generated, or parallel components multiply the 20–30-file merge passes.

**Setup on mac2:**
- Apple Silicon; ≥ 32 GB if it will run a simulator and an emulator together.
- Xcode 27 with the iOS 27 runtime; an "iPhone 17" simulator.
- Android SDK, API 35 arm64 image, and an AVD with the Pixel 9 profile.
- bun 1.4, fnm with Node 24.22.1, Java 17, CocoaPods 1.17.
- Clone at the same path (`~/Developer/oss/nitro-ui`, worktrees under `~/Developer/oss/nitro-ui-worktrees/`), so brief paths stay valid.
- Connect it to T3 Code as a second environment with the `codex_callstack` provider.
- Exclude the repo and DerivedData from Spotlight (A1 saw `mds`/`spindump` storms), disable sleep (`caffeinate` is already used), and run nothing else there.

**Sync and risks:**
- **Pushing.** Agents keep never pushing. The orchestrator pushes `task/*` or a SHA to a **private** remote, not to GitHub: the GitHub repo is public now, and WIP branches would be visible. For example, a bare repo on mac2 over SSH (`git remote add mac2 ssh://mac2.local/~/git/nitro-ui.git`). Bench jobs need only a SHA, and the runner refuses unless `HEAD == SHA` and the tree is clean (bench already refuses dirty trees for baselines). New baselines come back as a branch on mac2 that the orchestrator fetches and merges.
- **Two environments for the orchestrator.** Each `delegate_task` must target the right environment. Device UDIDs and ports differ, so they must come from that machine's lease, never from the brief. Keep `docs/tasks/machines.json` (env id → role, devices) and put `env:` in STATUS rows. Failure mode to guard against: delegating before pushing, so that the job benches a stale SHA. The SHA check above handles it.
- **Toolchain drift.** Two machines with different Xcode or CocoaPods versions produce false diffs. Pin versions in `CONTRIBUTING.md` and have `node-version.mjs`-style preflight checks for Xcode, pods and the system image.

**Expected speed-up:**
- Phase 1: about **15–25 % shorter calendar time for the same scope**. It recovers the ~15 h of quiet-window reservation and run-up per 4 days, shortens reviewed rounds by ~13 % (no in-round bench), and lowers load on the main machine, so fewer flake re-runs. It also stops baselines being refused.
- Phase 2: up to **~1.5× component throughput**, limited by review/merge serialisation and the owner's decisions rather than the machines.

## Appendix: method notes

- Delegation and review durations come from transcript tool-use timestamps and completion notifications (`/tmp/npr/timeline.py`). Coverage and idle time come from `/tmp/npr/cov.py`. The shell-time split comes from T3 `command_execution` items, using the union of intervals per thread and excluding long-lived emulator, Metro and log-stream processes (`/tmp/npr/cmds2.py`). Builds run inside harness, bench or real-input commands are counted under those gates.
- Conflict counts come from `git merge-tree --write-tree --name-only` on each branch's merge-main commit.
- Not measured: Apex token cost, and how much of the 26.7 h of model time went to report writing as opposed to code.
