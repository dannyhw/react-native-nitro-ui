# F1 dwell probe — how long a press must last to be delivered

Generated by `node scripts/real-input/dwell-probe.mjs` on 2026-10-29 (06:16–06:49 UTC), on the
`maintainer-mac-2` simulator pair (`iPhone Air` / iOS 27.0). Four runs, one `xcodebuild` launch per
row, 12 presses per row.

**How a press is judged delivered.** The witness is the control's *own* native `value:` — the
SwiftUI `Toggle` inside the component view — not a React-rendered echo. An echo can only move if the
touch reached SwiftUI *and* the event reached JS, so it cannot tell a dropped touch from a lost
event; the control's own state can. Each press is followed on the same launch by `js-toggle`, React
Native's own `Pressable`, pressed with the same shape: it says the event path was alive for that
launch. Every row below has `js-toggle` 3/3 except the Host-screen run, where that control is not on
screen and the tab's own anchor standing there plays the same part.

## What this says

1. **A zero-dwell touch is not "never delivered" — it is nearly never delivered on a busy screen.**
   0/12 and 1/12 on the Switch screen, but 1/12 on the Host screen and 3/3 for RN's own `Pressable`.
   The touch path is alive; the hosted control under load almost always refuses that shape.
2. **The drop is about how much is mounted, not only about the gesture.** At 0.03 s the *same*
   control answers 12/12 on a screen with a dozen controls and 1/12 on a screen with two hundred, at
   similar load. That rules out "SwiftUI Toggles ignore sub-frame touches" as the whole story and
   puts the loss between the window server and the recogniser on a screen with a lot to hit-test.
   Both screens are `ScrollView`s, so the review's UIScrollView touch-delay hypothesis is not
   contradicted by this — it is narrowed to the busy case. Which of the two it is needs the
   `delaysContentTouches` experiment, below.
3. **Load makes it worse at the short end and does not touch the long end.** At 0.05 s: 1/12 calm,
   0/12 loaded. At 0.08 s: 7/12 calm, 6/12 loaded. At 0.12 s: 12/12 both.
4. **A person's quick tap is inside the dropped band.** Common measured human tap durations are
   roughly 40–120 ms; 30–80 ms is 1/12 to 7/12 on the busy screen and 0/12 to 6/12 when the machine
   is busy. So the honest reading is: *a quick tap on a hosted Switch in a busy list can be dropped
   by the product*, which is the brief's stop condition — see `## Questions for orchestrator` in
   `F1-determinism.report.md`.
5. **120 ms is the measured floor for the test press.** 12/12 calm and 12/12 loaded, versus 0/12 to
   1/12 at a human's quick tap. The suite's `pressDwell` stays 0.15 s, just above that floor
   (`RealInputTests.swift:115`): the shortest value with no observed losses on either machine
   state, and the one every green run used. It is not below the reliable band, so it cannot make the suite flaky, and because every
   retry is now counted in the gate log (F1 M2), a floor that rises will show up as retry lines
   rather than as silence.

## What would settle the mechanism

Press at a fixed 50 ms on the Switch screen with `delaysContentTouches={false}` on its `ScrollView`,
and again with hit-testing made cheap (the same screen with the 200-row list removed). Whichever
change moves the 1/12 row to 12/12 names the cause. Both are one-line experiments in
`example/src/SwitchScreen.tsx`; they change app behaviour, so they belong to whoever owns the
product question, not to a determinism task.
