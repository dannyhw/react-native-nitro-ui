# X70 review: `ci-import` of the Android real-input job

Head `347e58d0`, base `origin/main` `5bf8f1b6`.

## What I checked

- Tests: `bunx vitest run scripts/__tests__/gate-ci.test.js` passes (21/21). The gate suites
  `gate*.test.js` and `bench-gate.test.js` pass (488/488).
- `node scripts/gate.mjs ci-import --run 45685481262` on this branch (clean, HEAD `347e58d0`)
  refuses for the head SHA and the matrix job names, prints `nothing recorded`, exits 1 and
  writes nothing.
- I ran mutations in a scratch copy of the tree (from `git archive HEAD`; the worktree was not
  touched). Results are in findings 3 and 7.
- I traced each path in the brief:
  - The SHA is checked three times: the run's `head_sha`, the record's `sha`, and the report's
    `vcs.commit`. A dirty worktree is refused, including untracked files.
  - The workflow path, the exact job name, and the run and job status are checked. A
    duplicate attempt is refused.
  - The verdict comes only from the upload, and it is stricter than a local run: a local run
    is green on exit 0 alone, while the import also needs the units file and the report to
    agree.
  - A completion is recorded only when the job's re-run arguments equal `planRerunFailed`'s.
    `completionProvenance` carries the red run's switches.
  - `foreignVerdict` is unchanged, and the line goes to the clone-wide record through
    `appendLedgerLine`.
- No regressions for other gates:
  - `GITHUB_ACTIONS` is unset on a local machine, so a local run records exactly what it
    did before.
  - No CI job runs `gate.mjs`: `check` runs as `bun run check`.
  - The new job has `if: github.event_name == 'workflow_dispatch'`, so it does not run on
    push, pull_request or merge_group.
  - The job only writes ignored paths (`.real-input/`, `example/e2e/.e2e/`, `build/`) and
    `$RUNNER_TEMP`, under `contents: read`. `ci-import` writes only `.gates/`, the clone-wide
    record, and a temp dir it deletes afterwards.
- `LEDGER_VERSION` 9:
  - Existing v8 greens stop counting on other branches. The `JUDGE_FILES` change already does
    that, so this costs nothing extra.
  - Older gate code ignores a v9 CI green, which it should: it does not know `source`.
  - v8 reds still decide.
  - `--rerun-failed` of a v8 red still works. Its completion has `relaxed`/`judge` null, as
    before.

## Findings

1. **Blocking.** An imported run that started before a newer line on this branch overrides
   that line.
   - Where: `scripts/gate.mjs` `commandCiImport` (around `:2311`, no check), with
     `scripts/gate-core.mjs:1020-1024`. `gateRowFor` lets the last appended own-branch line
     decide, but a CI line's `ts` is the hosted run's start (`gate-ci-core.mjs:390-399`), not
     the time of the import.
   - Scenario: CI run R of commit C starts at T1 and goes green. A local
     `gate.mjs real-input:android` on C starts at T2 > T1 and goes red. Then `ci-import --run R`
     appends the green last. This branch's row is green, and `need --for merge` passes over
     the newer red.
   - Another branch on the same digest sees red, because it picks by `ts`. I reproduced both
     rows with `gateRowFor`: own branch `green`, other branch `red`.
   - Two dispatches of the same commit do the same thing: import the red one first, then the
     older green one.
   - A local gate cannot record a green that started before a red already in the ledger.
     gates.md says a red "stays red until a newer full run on that digest … is green".
   - Fix: in `ciImportRefusals`, refuse when this branch's ledger has a `real-input:android`
     line (full run or completion) on the current gate digest whose `ts` is later than the
     run's start. Use the run's `run_started_at` from the API, or the record's `startedAt`.
     Add a test that imports an older green after a newer red.

2. **Blocking.** The artifact is not tied to the attempt that is checked and recorded.
   - Where: `scripts/gate.mjs:2342-2364`.
   - The import checks the newest attempt's jobs and writes that attempt and job URL into
     `source`. It then takes the first unexpired artifact named `real-input-android`, and
     `gh run download --name` picks one by name. Neither is matched to the attempt: the
     `artifact` it found is never used for the download.
   - Scenario: attempt 1 uploads a green. "Re-run all jobs" creates attempt 2, which fails at
     the emulator boot and uploads nothing (`if-no-files-found: warn`). If upload-artifact v4
     refuses a second upload of the same name, the outcome is the same. `ci-import` then
     passes attempt 2's checks and records attempt 1's green as "attempt 2", linked to a job
     whose conclusion is `failure`. A newer red attempt is hidden.
   - The duplicate-attempt guard does not stop this: one upload can be imported once per
     attempt.
   - The report lists this as a follow-up. It is the same false-green class as finding 1.
   - Fix: choose the artifact whose `created_at` falls inside the imported job's
     `started_at`…`completed_at`. Refuse when zero or more than one artifact matches.
     Download that artifact by id (`gh api repos/{owner}/{repo}/actions/artifacts/<id>/zip`
     is a read), and test it with two artifacts of the same name.

3. **Blocking.** No test guards the exit-code check on the full run or on the re-run.
   - Where: `scripts/gate-ci-core.mjs:223` and `:458-459`.
   - Mutations: `if (exitCode !== 0)` → `if (false)` at `:223`, and the re-run's `exitCode`
     → `0` at `:458`. With either one, `gate-ci.test.js`, `gate-evidence.test.js` and
     `gate-rerun.test.js` all still pass (21/21, and 97/97 together).
   - The exit code is the only thing that carries the whole-run checks: an e2e run error or
     the deadline, "the a11y sweep reported no cases", "no uiautomator check ran" and "a check
     failed" (`scripts/real-input/android.mjs:503-530`).
   - Scenario: a later change drops the exit check. A hosted run that hit the 63-minute
     deadline after every reported test passed then imports green, and nothing goes red.
   - Fix: add two tests and show each red under the mutations above:
     - the green fixture with `record.exitCode: 1` gives `result: 'fail'` and
       `why` containing `the run exited 1`;
     - `formRerun({ exitCode: 1 })` with units that pass gives a red completion whose
       `why` contains `the re-run exited 1`.

4. **Non-blocking.** A filtered or partial run in `full/` is recorded as the full gate.
   - Where: `scripts/gate-ci-core.mjs:203-252` and `:405-417`.
   - Neither `full.record.args` nor the units file's `selected` is checked against a full
     run. In a probe, `full/` with `args: ['--control','form']` and `selected: ['form']`
     imported as a green `node scripts/real-input/android.mjs` line. So did
     `selected: []`, which leaves only the a11y units.
   - `gate-ci.mjs run` always passes `[]`, so honest code cannot produce this. A local run,
     though, takes its canonical name from its own argv, and here the witness is right there
     and unread.
   - Fix: a full run is red, as evidence, unless `record.args` is `[]` and `selected` equals
     the ids in `REAL_INPUT_CONTROLS`.

5. **Non-blocking.** The import does not check that the tree stayed the same during the
   hosted run.
   - Where: `scripts/gate-ci-core.mjs:375-388`, with `before`/`after` read by
     `commandCiImport`.
   - `tree`/`treeAfter` are both read locally around a download, so `foreignVerdict`'s
     "unmoved" condition always holds for a CI line.
   - On the runner, only the app-stamp check at start and e2e's `vcs.dirty` stand in. A step
     or build that rewrites a tracked file during the suite would go unseen.
   - Fix: have `gate-ci.mjs` record `git status --porcelain --untracked-files=all` before and
     after each suite run in `run.json`, and make any change red.

6. **Non-blocking.** A CI line counts on other branches even when the job definition differs.
   - Where: `scripts/gate-core.mjs` `foreignVerdict` and `JUDGE_FILES`.
   - The green depends on `.github/workflows/ci.yml` (system image, AVD config, the steps
     between the run and the upload) and `.github/actions/setup`. Neither is in the gate's
     digest or the judge digest.
   - Scenario: branch A changes the job to an API 34 image and records a CI green. Branch B
     has the same `real-input:android` and judge digests but the API 35 job, and it takes
     A's green.
   - Fix: record the blob hash of `ci.yml` at HEAD in `source`, and in `foreignVerdict`
     require an equal hash for lines that carry a `source`. Or state the limit in "Runs on
     CI".

7. **Non-blocking.** Some guards survive mutation. Each needs a test case that goes red:
   - the report's `vcs.dirty === true` check, ignored (`gate-ci-core.mjs:273`);
   - two jobs named `Real input (Android)` accepted (`matching.length !== 1` → `=== 0`,
     `:104`);
   - the re-run's commit evidence dropped from the completion's `why` (`:464`). This is the
     CI form of "the digest was the same at the red run and the re-run";
   - the units-file half of the agreement dropped (`unit === 'pass' &&` removed, `:303`);
   - results that name unknown controls accepted (`:248`).

   The workflow-path, job-status and record-SHA mutations each turned a test red, as
   intended.

8. **Non-blocking (docs).** `docs/agents/gates.md` "Runs on CI" ends with "A red import is
   completed like any red run: `--rerun-failed` locally, or a new dispatch." A new dispatch
   is a new full run, not a completion. Suggested wording: "A red import is completed with
   `--rerun-failed` locally, or replaced by a newer full run from a new dispatch." That
   wording depends on finding 1, so that "newer" holds.

## Blocking

- 1: an older CI run imported after a newer red on this branch's digest becomes the deciding
  green.
- 2: the artifact is not tied to the attempt being imported, so another attempt's green can be
  recorded under a red attempt's job.
- 3: no test guards the full run's or the re-run's exit-code check, and it is the only thing
  that carries the whole-run checks.
