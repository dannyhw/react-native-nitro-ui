# X61 — `check`'s tooling tests never run while `prepare` regenerates `nitrogen/`

**Branch:** `task/X61-check-tooling-reads` (from `main` at `f4c8eef1`) · **Round:** 1 of up to 3 ·
**Lease:** none (no device)

## Summary

`test:tooling` read the committed `nitrogen/generated` tree (`patch-nitrogen.test.js` reads the
generated `.mm`/`.hpp` files, `app-stamp.test.js` reads the autolinker through
`registeredComponents`) while declaring `reads: []`. `prepare` (bob, `clean: "nitrogen/"`) deletes
and regenerates that directory, and nothing ordered the two, so the scheduler could run them side
by side and a tooling test saw ENOENT.

- `scripts/check-steps.mjs`: `test:tooling` now declares `reads: [nitrogen, nitrogen/generated]`
  (bob's clean removes the whole directory, so a reader of the generated tree reads both regions),
  and `prepare` needs `test:tooling` next to `test:library`. `findOutputConflicts(CHECK_STEPS)` is
  still `[]`.
- `scripts/__tests__/check-runner.test.js`:
  - New test "test:tooling declares every nitrogen/ region its tests name": scans every `.js`
    under `scripts/__tests__` and `eslint-rules/__tests__` (the vitest include dirs) for string
    literals starting `nitrogen/`, maps each to `nitrogen/generated` or `nitrogen`, and requires
    `test:tooling.reads` to contain each region. Fixture trees (copied to a temp dir before use)
    and `check-runner.test.js` itself (it names regions as expected strings, not reads) are
    skipped. This is the narrowest check that catches this case: an undeclared read is invisible
    to `findOutputConflicts`, and the scan sees the literal paths the reading tests use.
  - The "removing that edge" expectation now lists the two `test:tooling` conflicts.

The scan is conservative: some hits are paths written into temp repos (`gate-check.test.js`), which
only means the declaration is required for more than one reason; it cannot under-declare for a test
that names a `nitrogen/` path.
