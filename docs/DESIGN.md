# Design

How `react-native-nitro-ui` is built and why. This is the one design document: it describes the
library as it is now and is edited whenever the design changes. Using the library is in the
[README](../README.md); commands, gates and releasing are in [CONTRIBUTING](../CONTRIBUTING.md).

## 1. What this is

The library gives a React Native app the platform's own controls. Each component is a SwiftUI
control on iOS (a UIKit one where SwiftUI has none that fits) and a Jetpack Compose Material 3
control on Android, hosted in a Nitro Hybrid View: a native view whose props and methods are
written as a TypeScript spec and generated by nitrogen, Nitro's code generator. The control keeps
its own animation, gestures and accessibility. Layout stays with Yoga, React Native's layout
engine, because each control measures itself and reports its size to it. It runs on iOS and
Android under the New Architecture, in Expo development builds and bare React Native apps, as one
npm package with no manual native setup. It is not a cross-platform design system: it draws no
controls of its own, does not make the two platforms look alike, has no web target, and does not
run in Expo Go or on the old architecture.

## 2. Principles

1. Host the real control. Animation, gestures and screen-reader behaviour cannot be copied
   faithfully, so a component wraps the platform's control and never redraws it (D38).
2. Follow each platform. Props and behaviour follow the wrapped control, and a difference is
   documented, not hidden: a `Picker` wheel is SwiftUI's on iOS and a Material drum on Android.
3. Yoga owns layout. A control only says how big it is; a caller's `width`, `height` or `flex`
   wins, so the components compose with ordinary React Native views.
4. Native shows, React decides. Native displays an interaction at once, so there is no visual
   latency, and React stays the source of truth through the event count (section 3.5).
5. Performance is part of the contract. A hosted control is easy to make slow without any test
   failing, so the hot paths have fixed rules (section 3.3), partly enforced by lint.
6. Installing is `npm install` and a native rebuild. Consumers never patch dependencies or edit
   native projects by hand; an Expo config plugin is acceptable where it removes setup (D42).
7. Current platforms only. The version floor is set by what is worth using now (D39).
8. The public surface is small. Components, `prewarm`, `setMaterialTheme` and diagnostics are
   exported; Hybrid Views are not, so internals can change without a breaking release (D14).
9. Every workaround names its cause. A workaround for someone else's defect has an entry in
   [upstream.md](upstream.md) with the condition for deleting it.

## 3. How a component is built

Terms. Fabric is React Native's renderer, and its shadow node is the layout-side object for one
view. A host is the native view that owns one SwiftUI hosting controller or one Compose
composition. A model is the per-instance state object the hosted control reads. A commit is one
application of a batch of prop changes to the hosted control. `Switch` is the reference
implementation; read it first.

### 3.1 The files of one component

| Layer   | Core                                                              | Per component                                                                      |
| ------- | ----------------------------------------------------------------- | ---------------------------------------------------------------------------------- |
| Spec    | `src/NitroUiCore.nitro.ts`, `src/core/NitroUiIntrinsicProps.ts`   | `src/components/<Name>/<Name>.nitro.ts`                                            |
| JS      | `src/core/` (`useControlled`, `useStableCallback`, `useSizingId`) | `<Name>.tsx`, `NativeNitroUi<Name>.ts`, `NitroUi<Name>Config.ts`, `component.json` |
| iOS     | `ios/core/` (`NitroSwiftUIHost`, `NitroUiModel`)                  | `ios/components/<Name>/HybridNitroUi<Name>.swift`                                  |
| Android | `android/.../nitroui/core/` (`NitroComposeHost`, `NitroUiModel`)  | `android/.../nitroui/HybridNitroUi<Name>.kt`                                       |
| C++     | `cpp/NitroUiSizingEngine.{hpp,cpp}`, `cpp/NitroUiIntrinsic.hpp`   | none                                                                               |

`android/...` is `android/src/main/java/com/margelo/nitro`. The Kotlin Hybrid View stays in
package `com.margelo.nitro.nitroui`: the generated view manager finds it through a wildcard
import of exactly that package.

1. The spec declares props and methods. `bun run regen` runs nitrogen, which writes
   `nitrogen/generated/` (committed, so a consumer's build generates nothing), and then
   `scripts/patch-nitrogen.mjs`, which post-processes that output (sections 3.6 and 3.9).
2. `component.json` states what the control is: its sizing policy, whether a `Host` may hold
   it, which test sets it is in. `scripts/gen-registry.mjs` writes the per-component lists
   from it, among them `nitro.json`'s autolinking map and `nitro-ui.sizing.json`.
3. `NativeNitroUi<Name>.ts` is the raw host component with every spec prop required;
   `NitroUi<Name>Config.ts` copies the generated view config (`viewConfigs.test.ts` checks it).
4. `<Name>.tsx` is the public wrapper: friendly optional props in, every native prop out.
5. The Swift and Kotlin Hybrid Views each own a model and a host, and implement the generated
   spec class and `RecyclableView`.

### 3.2 Hosting: one host per view, created once

A Hybrid View creates its host in `init` and never replaces it: rebuilding a hosting controller
or a composition is the most expensive thing an update could do.

- iOS: `NitroSwiftUIHost<Content>` (`ios/core/NitroSwiftUIHost.swift`) is a `UIView` owning one
  `UIHostingController<NitroUiRoot<Content>>`. The content type is concrete, with no `AnyView`,
  so SwiftUI keeps structural identity. The hosted view is framed to the Yoga box and disclaims
  the safe area (`safeAreaRegions = []`), because React Native owns the keyboard and the insets.
  Only controls that present something (a menu, a picker) set `needsContainment`, which attaches
  the controller to the nearest view controller while the view is in a window. UIKit controls
  (`UITextField`, `UIListContentView`) sit in a `UIViewRepresentable` inside the SwiftUI content.
- Android: `NitroComposeHost<M>` (`core/NitroComposeHost.kt`) is a `FrameLayout` with one
  `AbstractComposeView` child and a fixed `Component(model)` composable. The wrapper is
  required: React Native measures a view before it has a window (inside a `Modal`, for
  example), and a detached `AbstractComposeView` throws when measured, so the host declines to
  measure until it has a window and a frame. The composition strategy is
  `DisposeOnLifecycleDestroyed`: the default disposes on detach, and React Native detaches
  mounted views during screen transitions and clipping.

A hosted control is its own composition, so `remember` shares nothing between controls. Objects
derived from the theme or a colour live in process-wide caches (`NitroUiColorSchemes`). The
library ships an ART baseline profile for its own classes (`android/src/main/baseline-prof.txt`).

### 3.3 Props: store, mark dirty, apply once

Props arrive on the UI thread as one batch per React commit. Nitro calls `beforeUpdate()`, one
setter per changed prop, then `afterUpdate()`. A setter only writes the model and calls
`host.markDirty()`. `afterUpdate()` reconciles the controlled value and calls `host.commit()`,
which invalidates the hosted control once: one `objectWillChange.send()` on iOS, one
`Snapshot.sendApplyNotifications()` on Android. Six changed props cost one SwiftUI body
evaluation, not six. What follows from this:

- The iOS model (`NitroUiModel`) is an `ObservableObject` with plain stored properties and a
  manual publisher, because `@Published` notifies per write. The Android model uses
  `mutableStateOf` only for fields the composable renders.
- Anything rendered marks dirty, including `accessibilityLabel`. Bookkeeping props (the value
  React sent, `mostRecentEventCount`, callbacks) do not, so an interaction re-applies nothing.
- Nitro does not order the props in a batch, so a setter never interprets its value against
  another prop: `Slider` stores `value`, the range and `step` raw and clamps in `afterUpdate()`.
- Spec props are never optional. Fabric sends `null` for a removed prop and Nitro treats only
  `undefined` as unset, so an optional prop that goes away crashes. Every prop is `T | null` and
  the wrapper always sends all of them (D7). Callbacks are the one exception (D7b).
- Props are typed values, never JSON strings or `AnyMap`; `Menu` items are a typed struct array.
  Nitro diffs props by identity, so an unmemoised object is re-sent on every render.
- Colours go through `useProcessedColor` and travel as an ARGB number. Native decodes the bit
  pattern, never the sign: `processColor` is unsigned on iOS and signed on Android (D10).

### 3.4 Events and stable callbacks

React Native cannot pass a function as a prop, so Nitro sends `{ f: fn }` and unwraps it only
when the spec type is a function. A callback prop is therefore declared `fn?`; `fn | null` is not
a function type and throws at mount (D7b). A callback runs asynchronously on the JS thread, and
native calls it after its own local write, so the control repaints before JS starts work.

`useStableCallback` (`src/core/useStableCallback.ts`) builds the `{ f }` wrapper once per mounted
view and swaps only the ref it calls, so a new inline closure from the app never changes the
prop. An inline `callback(...)` in JSX would re-send the prop on every render; the lint rule
`nitro-ui/no-inline-callback-in-jsx` rejects it. A callback the app may omit is still always
sent: `Slider` installs a no-op for a missing `onSlidingComplete`, so the prop keeps one
identity and is never `null` while mounted.

### 3.5 Controlled values: the event count

A controlled value is one that both the user and React can change. The handshake is
`useControlled` (`src/core/useControlled.ts`) in JS and `NitroUiControlledValue` on each platform
(`ios/core/NitroUiModel.swift`, `core/NitroUiModel.kt`):

- Native owns the displayed value and writes it at once on interaction. Each emitted change
  increments `nativeEvents`, and the event carries that count.
- JS echoes the newest count it has processed as the `mostRecentEventCount` prop, before calling
  the app's handler, so a handler that throws cannot strand native.
- In `afterUpdate()`, `reconcile()` accepts React's `value` only when `jsEvents >= nativeEvents`
  and it differs from what is displayed.

Native keeps the last value React sent apart from the displayed one, which is what makes a
rejected change revert: the app keeps `value={true}`, so the `value` prop does not change, but
the count does, the commit happens, and native restores `true`. A `value` written while an event
is in flight is dropped, not queued, so it cannot overwrite what the user just did. With `value`
undefined the control is uncontrolled: `defaultValue` seeds it once and an interaction costs no
React render. Values compare exactly, with no epsilon; a control that snaps quantises natively
before it emits, so JS and native hold the same bits.

A continuous control emits at most once per frame. `Slider` coalesces touch samples to the
newest value on a frame source (`CADisplayLink`, or a `Choreographer` callback) and calls
`user()` once per emitted event. Between a sample and the frame that emits it native holds a
value JS has not seen while the counts look equal, so `NitroUiControlledValue.unreported` makes
`reconcile()` refuse a write in that window. JS echoes only the latest count, so native never
waits for the counts to be equal.

The three implementations are tested with the same vectors (`useControlled.test.tsx`,
`scripts/native-tests/handshake.test.swift`, `NitroUiControlledValueTest.kt`), so a change to
one changes all three. A component with no user-editable value (`Progress`) uses none of it.

### 3.6 Intrinsic sizing

A generated Hybrid View is a plain Yoga leaf: with no style it is 0 by 0. The shadow node cannot
ask the control for its size, because layout runs off the main thread under Fabric's commit lock
while SwiftUI and Compose are main-thread only, and a synchronous hop can deadlock. So native
pushes sizes into a C++ cache and layout only reads it.

For every view listed in `nitro-ui.sizing.json`, `scripts/patch-nitrogen.mjs` repoints the
generated shadow node, state and component descriptor at `IntrinsicShadowNode`,
`IntrinsicViewState` and `IntrinsicComponentDescriptor` (`cpp/NitroUiIntrinsic.hpp`).
`bun run nitrogen:check` fails if a nitrogen upgrade changes the shape the patch expects.

```
measureContent (layout thread)       native host (UI thread)
  1 cache: this configuration          measures the control
  2 state: pushed to this node         NitroUiSizing.report(id, w, h, policy)
  3 guess: last size of this config    flush at the end of the turn:
  4 declared fallback                    corrects every instance laid out inexactly
```

- A configuration is the set of props a control's size depends on. The wrapper serialises it
  into `nuiSizingKey`: `""` for a `Switch`, variant, size and title for a `Button`. The engine
  adds the component name and an environment epoch itself. Two instances with the same key
  share one cached size, so a missing input is a wrong size.
- `nuiSizingId` identifies one mounted instance. `useSizingId` takes it from one native
  counter, because the engine is process-global and outlives a JS reload.
- The declared fallback is the control's documented size on the running OS: a `Switch` is 61 by
  28 pt from iOS 26 and 51 by 31 before. `NitroUiDeclaredFallbacks` registers it at startup,
  because Fabric measures a shadow node before it creates the view. It must be accurate:
  SwiftUI paints outside a box that is too small, and the overflow is dead to touches.
- The host reports what it measures. A report that matches what the instance was laid out with
  costs nothing. One that differs makes `flush()` correct every instance of that configuration
  with a Fabric state update: on iOS from a run-loop observer ordered before Core Animation's
  commit, on Android from a pre-draw listener that cancels the stale frame. So the first
  instance of a configuration may show the fallback for one frame (D17).
- Policy `intrinsic` asks the control what it wants under unbounded constraints. Policy
  `fillWidth` (`Slider`, `TextField`, a linear `Progress`) takes the box's width and asks for
  the height at that width; if that height depends on the width, the width goes in the key.
- The wrapper's base style follows the policy. `useSelfSizingBaseStyle()` gives an `intrinsic`
  control `alignSelf: 'flex-start'` (`'center'` inside a `Form.Row`), because Yoga stretches a
  measured leaf on the cross axis anyway; a `fillWidth` control uses `alignSelf: 'stretch'`.
- On iOS a commit is not a measure point. A setter whose prop can change the size calls
  `host.noteContentSizeMayHaveChanged()` beside `markDirty()`, or the engine is never told. On
  Android, Compose's own measure pass reports the new size.
- An environment change (text size, density, locale) bumps the epoch and clears the cache;
  mounted instances are re-measured and corrected. An instance that was once corrected
  re-measures on later props-only updates (D20).
- `prewarm(['NitroUiSwitch'])` adopts a declared size as a provisional cache entry, so the first
  mount of a default configuration needs no correction. A measurement still replaces it.

### 3.7 Recycling and drop

React Native may reuse a native view for another component instance. Every Hybrid View
implements `RecyclableView`, and both platforms must be correct after a bare reset:

- `prepareForRecycle()` resets everything a setter writes (iOS lists the fields; Android calls
  `model.reset()`) and re-arms per-mount flags, such as the one that disables animation on the
  first commit so a reused row does not animate from the previous row's value.
- `onDropView()` releases callbacks first, since they hold JS references, then calls
  `host.drop()`, which hands the sizing id back with `NitroUiSizing.forget(id)`.
- iOS keeps the hosting controller and its SwiftUI state across a recycle. Android disposes the
  composition in `drop()`, which runs before the reset, so a recycled Android view composes
  again from the reset model. Android recycles only when the app turns on React Native's
  `enableViewRecycling` flag; with it off, every drop is a real unmount.
- Whatever a host registers on a longer-lived object, `drop()` undoes. On Android the
  composition strategy observes the activity's lifecycle and the sizing listeners sit on the
  window's `ViewTreeObserver`; either one left behind retains the host. Arm at attach, undo at
  drop, never at pool entry.

### 3.8 Threads and imperative methods

Host code runs on the main thread only (`nitroUiAssertMainThread`). A method JS can call never
touches SwiftUI or Compose from the JS thread: `measureContent()` reads a size cached on main.
The props path makes no synchronous hop in either direction, and no `main.async` when already
on main, which costs a frame.

`hybridRef` is an internal, read-only handle for the test harness and benchmarks; a prop written
through it runs the setter on the JS thread and never commits. An imperative method is a method
on the wrapper's `ref` with an explicit hop: `TextField`'s `focus()` and `blur()` post to the UI
thread and act there.

### 3.9 Views with children, presented surfaces and `Host`

A generated Hybrid View is a leaf. A component that holds React Native children (`BottomSheet`,
`Popover`, `ContextMenu`, `Form`) has a hand-written Android `ViewGroupManager`, named in its
manifest's `androidViewManager`, and on iOS `scripts/patch-nitrogen.mjs` gives the views in
`CONTENT_CHILDREN_VIEWS` overrides that mount children into the content view. These components
have `sizing: null`: their box comes from style or from their children. `Form` scrolls its rows
natively, so its shadow node is `ScrollShadowNode` (`cpp/NitroUiScrollShadow.hpp`), which makes
`measure()` of a row account for the scroll offset.

Presented surfaces on iOS use `NitroUiPresentation` (`ios/core/NitroUiPresentation.swift`), which
presents from a window of its own. UIKit lets a view controller present one thing at a time, so
a dialog, tooltip or popover in the app's own chain would block or strand a React Native `Modal`
(D41). `BottomSheet` uses the screen's chain unless a `Modal` is on top (D35).

`Host` is an opt-in container that composes its direct nitro-ui children into one Compose
composition on Android, which removes the per-control composition cost (D23, D24); on iOS it is
a plain `View`. A hosted control builds no composition of its own and is never measured. The
allowlist exists twice, because React flattens wrapper components away: `HOSTABLE_CONTROLS` in
`src/components/Host/HostChildren.ts` and the `isHostable` override on the Android host.

### 3.10 Theme and icons

Android content is wrapped in `NitroUiTheme` (`core/NitroComposeHost.kt`): Material 3 Expressive
over the device's dynamic colours, light or dark with the system. `setMaterialTheme('baseline')`
switches the whole process to the baseline Material theme; there is no per-control theme prop.
iOS controls take the system appearance, and a `tintColor` where SwiftUI honours one. Icons are
`systemImage` (an SF Symbol name) on iOS and `androidIcon` on Android: a vector drawable `.xml`
imported as a Metro asset, or the name of a drawable the app ships. The wrapper resolves it to a
string in `src/iconSource.ts` (D43).

### 3.11 Accessibility and `testID`

- The label goes on the control, never on the container: `Modifier.semantics` on the Material
  control, `.accessibilityLabel` on the hosted SwiftUI element, applied only when set. On the
  container it would add a second, empty focus stop and leave the control unnamed.
- `testID` reaches iOS through React Native's own `accessibilityIdentifier`, so the host does
  not set it again. Compose has no such path, so on Android it lands on the host's `View.tag`.
- Leftover `ViewProps` are spread onto the Fabric container. Setting `accessible` or
  `accessibilityRole` there can hide the hosted control from the screen reader.

### 3.12 Proving a component

The steps and commands are in CONTRIBUTING, "Adding a component". What the design requires:

- Lint (`eslint-rules/`) holds four rules of the perf contract: no inline callback, no optional
  view prop, no `AnyMap`, no JSON-string prop. The rest is reviewed against section 3.3.
- A `<Name>.perf-test.tsx` counts wrapper renders for a scenario, and `bun run check` compares
  the count with `bench/baselines/renders.json`. Eight components have one.
- On-device harness tests (`example/__tests__/<Name>.harness.tsx`) use real taps and assert
  counts, not wall-clock time (D21). Sizing counters (`nitroUiCore.sizingStats()`) are read as
  deltas, because the engine is process-global, and sizing tests seed a wrong fallback so a
  failed correction is visible. The engine itself is tested on the host in
  `scripts/native-tests/sizing.test.cpp`, under AddressSanitizer.
- The conformance suite (`example/__tests__/Conformance.harness.tsx`) checks four recurring
  defects for every manifest: the label on the node a person acts on, no leak on drop, a
  registered fallback whose correction can be seen, and a full recycle reset.
- A new test is shown to fail once, by breaking what it guards, before it is trusted.

### 3.13 Build constraints

- The Compose compiler plugin version equals the host app's Kotlin version
  (`android/build.gradle`).
- The podspec's iOS target is React Native's `min_ios_version_supported`. A target above the
  app's is rejected by CocoaPods, so newer SwiftUI API is gated with `#available`.
- The example app's Gradle paths point at the repository root's `node_modules`, and a release
  build needs `hermesCommand` set there (`example/android/app/build.gradle`).
- A Swift file that uses Nitro's `NullType` imports `NitroModules`.
- The Nitro peer range `^0.37.1` means below 0.38.0: a Nitro minor is a breaking change here.

## 5. Decisions in force

Code comments and other documents cite these numbers. A number that is absent was dropped as
obsolete; a few that are still cited elsewhere are kept as one line naming what replaced them.

### API

- D7. No optional (`?:`) Hybrid View props. Specs use `T | null` and the wrapper passes every
  prop, because a removed prop arrives as `null` and crashes an optional one (nitro#1184).
- D7b. Callback props are the exception and must be optional (`fn?`): Nitro unwraps `{ f }` only
  for a pure function type, and `fn | null` throws at mount.
- D10. Colours cross as `processColor` numbers; native decodes the bit pattern, never the sign.
- D14. Hybrid View types and `hybridRef` are not public; every prop flows through React on the
  UI thread. An imperative method is a wrapper `ref` method with an explicit main-thread hop.
- D16. A measured size is an explicit size, so cross-axis stretch is opt-in with
  `alignSelf: 'stretch'`. `prewarm` covers default configurations only.
- D29. `Menu` has no value, no handshake and no imperative `open()`. Items are a typed nested
  `group` (sections, one submenu level), never child views. With `primaryAction`, iOS runs it
  on tap and opens on long press, and Android draws a split button.
- D32. SwiftUI's `Menu` has no expansion binding, so `onOpen` and `onClose` fire on Android only,
  as does closing on `disabled`. A pick fires `onSelect`, then `onClose`.
- D33. The dialogs are `AlertDialog` and `ConfirmationDialog`, not `Alert`, which is React
  Native's name. A dismissal the app refuses (`isPresented` stays true) presents again with a
  development warning. `BottomSheet` content is mounted only while presented.
- D34. `TextField` hosts `UITextField` on iOS: only UIKit exposes marked text, which the guard
  that drops a JS write during IME composition needs.
- D35. On iOS `BottomSheet` presents in the screen's presentation chain, and from its own window
  only when the top presented controller is a React Native `Modal`.
- D36. `ContextMenu` is a `View` that opens `Menu`'s `group` on a long press, with its children
  in place, no value and no `open()`. It is an accessibility element only if the app sets
  `accessible`. `Menu` and `ContextMenu` share their row code.
- D37. `ContextMenu` sends the flattened `borderRadius` as `previewCornerRadius`. Screen-reader
  reach is verified by automation only: no test waits on a person.
- D38. Where a platform has no control, build it from that platform's real controls and document
  it; never draw an imitation, which is why there is no toast. `Tooltip` is data and `Popover`
  holds React Native content. `Picker`'s `radio` variant falls back to the menu on iOS.
- D40. Each Android control uses its Material 3 Expressive counterpart where one exists. Android
  icons are an `androidIcon` prop beside iOS's `systemImage`.
- D41. `Tooltip` and `Popover` present from their own window on iOS, because a popover in the
  app's chain makes UIKit refuse the next React Native `Modal`.
- D42. The size ladder is `small` to `xxlarge`, shared by `Button` and `IconButton`. Toggles in
  a connected iOS `ButtonGroup` fall back to a row of bordered toggles. An Expo config plugin is
  allowed where it makes the library better; what is ruled out is a lot of manual setup.
- D43. Icons are never drawn by hand. The library's own Android icons are official Material
  Symbols files copied by `scripts/icons/fetch-material-symbols.mjs`. `androidIcon` takes a
  vector drawable as a Metro asset or a drawable name. There is no combined `icon` prop.
- D44. A `Popover`'s content lays itself out in place and native reads its box. A popover
  dropped while presented follows `BottomSheet`'s drop rule.
- D45. `Form` and `Section` are native containers holding ordinary React Native rows. There is
  no virtualized native list; long lists use FlashList or Legend List.
- D46. `ListItem` is the row-content leaf, with no control accessories. Inside a `Form.Row` the
  row owns shape, padding and press, and the leaf owns the content.
- D47. `Checkbox` on iOS is a `Toggle` whose style draws SF Symbol checkmarks. `iosStyle` is
  `'circle'` (the default), `'square'` or `'switch'`.

### Performance

- D1. `nitroUiCore.now()` is `CLOCK_UPTIME_RAW` on Apple and `CLOCK_MONOTONIC` on Android, the
  base of the display's frame timestamps. Benchmark code uses the same base.
- D17. The first instance of a sizing configuration per environment may show the declared
  fallback for one frame; an instance whose configuration is already cached lays out exactly on
  its first frame. A flush makes at most 2 synchronous corrections on iOS and 1 on Android.
- D20. An instance whose size was ever corrected re-measures on later props-only updates,
  because React clones from its pre-correction revision. Other instances pay nothing.
- D23. `Host` is opt-in, because inside it controls are native content and not React Native
  views. It works on Android only: a shared iOS host lowered memory but raised mount and unmount
  UI-thread CPU, so the iOS `Host` is a passthrough `View`.
- D24. A hosted control never measures its content and never reports, so D17 does not apply to
  it. Yoga still gives it a frame, but nothing is drawn with that frame. The `Host` places its
  children in one column from its top-leading edge, clipped to its box, and measures nothing
  itself: give it a height. Of its own styles only size and `padding` reach the drawing.

### Testing and benchmarks

- D9. Device benchmarks compare the candidate with the newest release in one session on one
  device (`--compare-release`), the two sides alternating. A cell fails when the candidate's
  ratio to the release is over 1.20, its confidence interval excludes 1.05 and the cell was quiet
  within the run. No device timing is committed, and load is recorded with the run, not refused
  on. Device benchmarks inform review; wrapper render counts are the hard gate
  (`bench/baselines/renders.json`, in `check`).
- D15. The canonical iOS benchmark device is an iPhone 17 simulator. The target is at most 1.0×
  `expo-ui-shared-host`, and well below `expo-ui-host-per-control`, on mount latency, UI-thread
  CPU and memory; a miss needs an explanation. The numbers are in [performance.md](performance.md).
- D18. Android benchmark numbers compare only within one ART compilation state, which every
  run records.
- D21. On-device tests assert structure: counts of corrections, flushes, stale frames, events.
  Wall-clock thresholds run only under `HARNESS_TIMING=1` on a quiet machine.

## 6. Known limits and upstream defects

Each has an entry with evidence and a removal condition in [upstream.md](upstream.md). The
per-control limits a user meets are in the README's "Known limitations".

- Nitro 0.37 delivers a removed prop as `null`, which crashes an optional prop (N2), and callback
  props must be optional (N3). These are D7 and D7b.
- Nitro 0.37.1 drops React Native's base `ViewProps` on Android (N1). The patch script adds the
  missing call, with `cpp/NitroUiPropsCompat.hpp`, until Nitro 0.37.2 is the floor.
- Nitrogen has no hook for a custom shadow node (N6), so sizing post-processes generated code.
- The generated Android view manager draws no border or radius (N4); wrap the control in a `View`.
- Android applies props twice to every new view (N5): two `propsApplied` marks per mount is the
  floor, not a defect.
- One hosting controller per control costs more memory per instance on iOS than a shared host,
  with no known fix (D23). On Android the same cost is what `Host` removes.
- `prewarm` cannot seed a configuration whose key is not empty, such as a `Button` title, so
  the first instance of one shows its fallback for a frame.
- The test harness cannot press a control inside a React Native `Modal` and has no drag (H9,
  H11), so those paths are tested with OS-level input or test-only methods.

## 7. Open questions

- Borders and corner radius on an Android Hybrid View: draw them in Compose, or keep the
  documented wrapping `View` (upstream N4).
- Which iOS presentation `BottomSheet` should use. It presents in the screen's chain (D35);
  `Tooltip` and `Popover` use their own window (D41) because of a hazard nobody has measured for
  a sheet, and in its own window a `fit` detent does not follow the content.
- Whether the controls a `Host` refuses only because nobody measured them inside one
  (`TextField`, `SearchField`, `Chip`, `Checkbox`, `IconButton`, `ButtonGroup`, `Stepper`,
  `ListItem`) should be hostable.
- Pre-warming configurations other than the default, which needs sizing keys per component.
- A UI-thread path for high-frequency values, such as a `Slider` driven by an animation without
  a React render per frame. None is designed.
- Whether the iOS benchmark should judge total main-thread work per mount instead of time
  inside the mount transaction, which penalises measuring synchronously at mount.
