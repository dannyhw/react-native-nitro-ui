---
'react-native-nitro-ui': patch
---

Fixed a per-instance memory leak in the sizing engine that a scrolling list hit once per dropped control. A size correction is an asynchronous Fabric state update, and React Native runs its callback _later_ — scheduling a layout pass over the tree revision that carried it. If the view is dropped in between, as it is on every row that scrolls off, that pass lays the instance out one more time and the engine recorded what it laid out in that instance's ledger entry. Nothing reclaimed the entry afterwards: the engine's cleanup walk looks for `State` objects that died without being forgotten, and a forgotten instance has no registry row to be found in. One entry per occurrence, for the life of the process, on top of the leak being visible to `sizingStats()`.

A layout arriving for an id the engine has already finished still returns the size it would have returned — the layout itself is real and Yoga still commits it — but its per-instance state is now _held_ rather than written to the ledger. Held where, and why not simply dropped: an id is only new per **React** mount, not per native one. iOS creates no native view for a `display: none` node, so hiding a control deletes its view and finishes its id, while showing it again lays a new native view out under that same id, one step before the mount that re-binds it. Dropping the state that layout produced would leave the control bound with nothing for its measurement to correct against — a `sizingKey` change or a font-scale change after a hide/show would then have no effect for the rest of its life. So the entry waits, off the ledger, for a bind that claims it; a bind that never arrives is released after a second, and at most 256 are held at a time. An id that is genuinely still in flight, laid out a moment before it binds, is untouched and still gets its correction. Found by the `Menu × no-leak-on-drop` conformance rule on a GitHub hosted runner, where `50` drops left `1` ledger entry and the registry read `0`.

A second route to the same leaked entry, found by `Picker × no-leak-on-drop` on the next dispatch: a layout for an instance whose mount _never arrives_. `measure` is the only place a ledger entry is created, and it creates one for any id — bound or not — because layout legitimately runs on the shadow thread before the mount transaction binds. When the commit that laid the node out is dropped, neither of the engine's reclaimers is ever told: `forget` comes from `onDropView`, and a view that was never created has no drop to call it, and the cleanup walk looks at the registry, where an id that never bound has no row. That walk's own trigger was the second half of the bug — it fires once the registry has _grown_ by a stride, and an entry that never binds is precisely one that never grows it. Such an entry was therefore permanent, one per occurrence, on a tree that already had the fix above.

An entry filed for an id that is not bound yet is now owed the same second-long grace a held layout gets, and when it closes the entry is _demoted_, not deleted: it leaves the ledger, which stops the leak, and joins the held set, where a bind that is merely very late — on a runner saturated enough to take longer than the grace between a layout and its mount — claims it back with its correction intact. Deleting it would have been one line shorter and would have frozen such a control at its fallback size for the life of its mount. The grace is checked on flush as well as on layout, because the workload that leaks is a churn that has already stopped, and nothing lays out afterwards. The cleanup walk's trigger now follows the registry down as well as up, so emptying a screen (a dismissed modal, a list whose data was replaced) cannot leave that walk quiet until enough new views are mounted to reach the old number.
