`ButtonGroup`: a row of commands — _Copy | Paste | Share_ — optionally with independent toggles — _Bold | Italic | Underline_ — that moves the items it cannot fit into an overflow menu.

- **Items are data, and the row reports their ids.** `{ id, title, systemImage, androidIcon, disabled, toggle, checked, defaultChecked }`, in render order: `onPress(id)` for an action, `onCheckedChange(id, checked)` for a toggle, and the same event whether the item was in the row or reached through the overflow menu. The items cross to native as one typed struct array — no JSON string, no `AnyMap` — and every field is always sent, so a recycled view can never be handed half a row.
- **Each item decides its own controlled-ness.** An item whose `checked` is a boolean is controlled; one where it is `null` or absent is not, and native keeps whatever the user gave it, seeded once from `defaultChecked` and then forgotten so a re-render cannot undo the tap that just happened. A toggle is painted _before_ React sees the event and snaps back if the app refuses it — `docs/architecture/core.md` §4's handshake, with one event count for the whole group rather than one per item, so one item's stale write cannot be accepted on another's confirmation.
- **`appearance: 'connected'` is the platform's own joined row.** Android gets Material's `ButtonGroup` with `customItem`, because `clickableItem` and `toggleableItem` hard-code a filled button and could not carry `variant`, `size` or `tintColor`. iOS gets SwiftUI's `ControlGroup` — and three rules that came from probing it rather than reading about it: it ignores `.controlSize`, `.tint` and `.buttonStyle` (174.00 × 31.00 pt at every size, every tint and three button styles), and it draws **no on state** for a `Toggle`, so a connected iOS group whose items include a toggle falls back to the standard bordered row. Same props, same events, a row that tells the truth. Android keeps its connected toggles, because Material's `ToggleButton` has a checked container.
- **Overflow is decided by the box, on both platforms.** Six items that overflow at 220 pt are a full row across the screen. Android uses Material's own indicator and menu; iOS has nothing to borrow, so the row is a `ViewThatFits` over "all items", "n−1 items plus a `Menu`", and so on — with the `Menu` _beside_ the group, because inside a `ControlGroup` its segment measures but never opens. `ButtonGroup` is `fillWidth` for exactly this reason: an intrinsically measured row would measure unbounded, decide nothing overflowed, and draw outside a box Yoga had already clamped. On iOS 15 there is no `ViewThatFits`, so the row clips instead — documented, and better than drawing outside.
- **A row that overflowed is still readable.** `overflowAccessibilityLabel` names the control a reader reaches when the row has hidden half its commands. Android's indicator already arrives named — Material calls it "More options", in the reader's own language — so with no label this one leaves Material's semantics alone and only _replaces_ them when you name the control yourself; iOS draws `'More'` because it has nothing else to draw. Changing the label after mount now reaches the row as well: it was a plain field, so the new words were stored and never painted.
